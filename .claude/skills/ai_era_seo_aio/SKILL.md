# ai_era_seo_aio

**AI 検索時代に引用され、かつ従来検索でも勝つ**ためのコンテンツ / サイト設計スキル。

## 大原則 (これを外すと全部ずれる)

1. **AEO / LLMO / GEO は SEO と別物ではない。** Google 公式が明言している (`guide.md` §1-2)。
   「LLMO 対策」という別プロジェクトを立てない。SEO の土台の上に「引用される要素」を足す
2. **現在の taitech.dev の作りを正としない。** 既存ページの大半は `guide.md` の観点を意識せずに
   作られている。「既存がこうなっているから」は根拠にならない。既存実装は
   **参照する対象であって、準拠する対象ではない**
3. **`guide.md` の数値は多くがツールベンダーの自社調査で、相関は因果ではない。**
   優先順位を決める地図として使い、断定の根拠にしない。ユーザーに説明するときも同じ温度で話す
4. **一次情報を読む。** このファイルは索引と翻訳であって、条文ではない。判断が要るときは
   `references/guide.md` の該当節を開く。節番号はこのファイル中に埋めてある

## このサイト固有の前提 (毎回ここを踏まえる)

### 何が非コモディティ資産か (`guide.md` §3-2 の当てはめ)

Google が第一条件に挙げるのは「コモディティでないこと」。このサイトが持てるのは 3 つ。

| 資産 | 実体 | AI 引用における弱点 |
|---|---|---|
| **動く教材** | Playground / 可視化 / トランスパイラ / クイズ | **LLM は動作を読めない。テキストしか引用されない** |
| **講師としての一次情報** | 個別指導で実際に出た誤答・質問・つまずき | 現状ほとんどテキスト化されていない |
| **厳密な定義文** | `topics.*.ts` の `definition` | 定義自体は他所にもある。差別化は例と誤解の説明側 |

**最重要の含意**: このサイトの売りである「動かして確かめられる」は、**そのままでは AI 検索で
ゼロ点**。Playground を置いたページほど、

- 動かすと何が観察できるのか
- その観察から言える結論は何か
- なぜ多くの人がそこを間違えるのか

を **本文テキストで言い切る**必要がある。これを欠くと、AI から見て「よくある解説記事」と
区別がつかない (`guide.md` §3-4 / §3-5)。

理由は「LLM が動作を読めない」だけではない。**CodeEditor は `ssr: false` なので、
中のサンプルコードは初期 HTML にすら存在しない** (下記「デザイン投資の位置づけ」)。
AI から見ると Playground ページは、本文テキストの分しか無いページに等しい。

### 「独自データ」の現実的な代替

このサイトは自社サービスの集計データを持たない。代わりに一次情報として作れるのは:

- 個別指導で実際に出た**誤答・質問の分布** (「この設問は 3 人中 2 人が添字を間違える」)
- 実行環境での**実測ログ** (EXPLAIN の実出力、分離レベルごとに実際に走らせた結果)
- 試験の**出題傾向の自前集計** (年度 × 分野で数えたもの)

いずれも「経験 (Experience)」に直結し、競合が模倣できない (`guide.md` §3-3)。
一般論を書きたくなったら、まずこの 3 つのどれかに置き換えられないか考える。

### サイト外シグナル — ここが最大のレバー (`guide.md` §5)

`guide.md` の中で**最も行動を変えるべき章**。自社サイトのリライトより外部言及のほうが効く
ケースが多い (Ahrefs 75,000 ブランド調査で被リンク 0.218 に対し YouTube 言及 0.737 / ブランド
ウェブ言及 0.664)。

ただし個人サイトなのでプレスリリース・第三者ニュースメディア掲載は非現実的。
**使える面は限られる**:

| 面 | 状態 | 判断 |
|---|---|---|
| **YouTube** | 未着手 | `guide.md` で単一最強の相関。`taitech-post-video` で短尺は作れるので **最短のレバー**。提案する価値が最も高い |
| **Qiita / Zenn** | 運用中 (`../qiita/` `../zenn/`) | 第三者ドメイン掲載に相当 (§5-3 の 8% → 34%)。**AGENTS.md の重複禁止と衝突させない**。同一本文を出さず切り口を変える |
| **X** | 運用中 (`taitech-x-posts`) | 指名検索とブランド言及の供給源。直接引用は狙わない |
| **Reddit** | 対象外 | §5-5 のデータは英語圏前提。日本語教材では母数が薄い。無理に狙わない |

**やってはいけない**: 言及の買い付け、権威指標ベースの大量ゲスト投稿、ニッチエディット。
2026 年 5 月に Google はスパムポリシーの定義を AI Overviews / AI Mode に拡張しており、
**AI 回答の操作はスパム** (`guide.md` §8-3)。

### デザイン投資の位置づけ (`guide.md` §4-7 の当てはめ)

**「見た目をよくすれば SEO / AEO に効く」は、このサイトでは成立しない。** `guide.md` §4-7 の
影響度は、内容を 10 としたとき SEO で 0.5〜3、AEO の視覚デザインで 0〜0.5。一方、
技術実装のミスは加点ではなく **×0** になる。**上限は低く、下限は 0** という非対称が本質。

このサイトのモノクロ・低装飾の作りは **AEO 上はむしろ有利側**。装飾を厚くする提案はしない。
効くのは「機能としての UX」(表示速度 / 見出し階層 / セマンティック HTML / 初期 HTML)。

#### このサイトの資産は §4-7 の罠の真上にある

| 資産 | §4-7 のどの罠か | 実際のところ |
|---|---|---|
| **Playground の CodeEditor** | `ssr: false` の dynamic import | **エディタ内のサンプルコード・擬似言語は初期 HTML に無く、AI から完全に不可視**。ページ本文で結論を書く必要があるのはこのため |
| **viz / 図解の inline SVG** | 「画像内テキストは読まれない」 | **当てはまらない**。`<svg><text>` は client component でも SSR されて初期 HTML に入るので AI も読める。ここを画像 (`<img>` / canvas) に置き換えるのは可視性の後退になる |
| **クイズ・アコーディオン系 UI** | 「初期 HTML に無ければ届かない」 | 解説文を開いたときだけ描画する作りにすると AI から消える。**DOM には出して CSS で隠す**のが正解 |

**新規コンポーネントの判定基準はひとつ**: そのテキストが「JS 実行前の HTML にあるか」。
`curl` で確認できる。`ssr: false` を足すときは、**その中の情報が失われても本文だけで
成立するか**を必ず確認する (エディタ本体は道具なので `ssr: false` で問題ない)。

### 検索意図の分布

このサイトのクエリはほぼ **Know** (「〜とは」「わかりやすく」) と **Do** (動かしたい / 解きたい)。
Compare / Buy は `/books` だけ。`guide.md` §6 の「業種ごとの引用の指紋」に教育分野のデータは
無いので、**推測せず GSC で自前に測る** (`taitech-analytics`)。

## §A. design — 新規コンテンツを作る前に

書き始める前に、この 6 問に答える。答えられない項目があるならまだ書かない。

1. **狙う意図とページ型は一致しているか** (`guide.md` §3-6)
   Know なら定義 + 図解、Do なら手順 + 動かせるもの、Compare なら比較表
2. **そこにしかない情報は何か** — 上記「独自データの代替」3 つのどれかを 1 つ以上入れる
3. **結論は冒頭にあるか** — 一般論の前置きで文字数を稼がない (`guide.md` §3-5)
4. **数値と出典が入っているか** — Princeton の GEO 研究では引用・統計・引用文の追加が
   AI 可視性を 30〜40% 押し上げた (`guide.md` §3-4)。**新旧 SEO で完全に利害が一致する数少ない施策**
5. **既存ページとカニバらないか** — `topics.*.ts` の `keywords` を grep する。
   前例として `/why-need-rdb/concurrency` は `分離レベル` を意図的に外して
   `/why-need-rdb/isolation-levels` に譲っている (同ファイルのコメント参照)
6. **動く要素の結論をテキストで書いたか** — 上記「最重要の含意」

### 実装時に必ず埋めるもの

- `metaTitle` / `metaDescription` — 狙うクエリを含む長文はこちらに分離する。
  `title` / `label` はナビ用に短く保つ (既存の設計意図。`sections.ts` のコメント参照)
- `definition` — 厳密な定義。AI が引用しやすい単位
- `keywords` — カニバリ判定の索引としても機能する
- JSON-LD — `src/components/seo/JsonLd.tsx` の既存ジェネレータを使う。**新規に手書きしない**
- セマンティック HTML と見出し階層 — Google は DOM 構造とアクセシビリティツリーを
  直接見ている (`guide.md` §4-2)。ラベルのない `<div>` の入れ子は可視性を損なう

## §B. review — 既存ページ / サイトを診断する

`guide.md` §10 の優先順位で見る。**優先度 1 が欠けていると他が全部無効**なので順番を守る。

### 優先度 1: 取得可能性

`robots.ts` は全許可、`sitemap.ts` は全ページ列挙済み。ここは基本的に問題ない。
確認するのは以下だけ:

- 新規ページが `sitemap.ts` に入っているか (手動列挙の箇所がある。追加漏れが起きうる)
- `nosnippet` / `max-snippet` で自らスニペットを塞いでいないか
- **JS 実行“前”の HTML に本文があるか** — Googlebot は JS を実行するが、GPTBot /
  ClaudeBot / PerplexityBot は**実行しない** (`guide.md` §4-7)。AEO ではここが ×0 か ×1。
  確認は `curl -s https://taitech.dev/<path> | grep <本文の一節>`。
  `ssr: false` の dynamic import と、開いたときだけ描画するアコーディオンが主な発生源

### 優先度 2: コンテンツ

§A の 6 問をそのまま診断項目として使う。加えて:

- **執筆者・更新日が可視か** — `site.author` と `AuthorJsonLd` はあるが、
  ページ本文に見える形で出ているかは別問題 (`guide.md` §3-3 Trustworthiness)
- **そのページで検索が終わるか** — NavBoost が報いるのは滞在時間ではなく
  「ここで探し物が終わった」状態 (`guide.md` §4-7)。順位が上がらない相談では、
  **読みやすさではなく「答えに到達するまでの距離」**を疑う。
  結論が下にある / 前置きが長い / 次に何を読めばいいか示していない、が典型

### 優先度 3: サイト全体

- トピッククラスター: `topicsInSection` / `RelatedTopics` / `PrevNext` で結べているか
- 構造化データが**可視情報と一致しているか** (`guide.md` §4-4)

### 既知の検討事項 (断定ではなく、レビュー時に必ず思い出すこと)

**鮮度メタデータがビルド日に固定されている。**
`JsonLd.tsx` の `dateModified` は `BUILD_DATE`、`sitemap.ts` の `lastModified` は `now`。
つまり**ビルドするたび全ページが「今日更新」になる**。

- `guide.md` §4-4 は「構造化データは可視情報と一致している必要がある」としている。
  ページに更新日表示が無い状態で全ページ今日更新を主張するのは、この原則から外れる
- §3-7 は AI 検索での鮮度の重要性を挙げているが、**実際の更新頻度の情報を失う**設計でもある

これは「直せ」ではなく「レビュー時に俎上に載せろ」。実際に変えるなら、コンテンツ側に
更新日を持たせて可視表示と JSON-LD の両方に流すのが筋。ユーザーの判断を仰ぐこと。

## §C. judge — 施策の価値を判定する

**やる前に Mythbusting ゲートを通す。** Google が明示的に「無視してよい」としているもの
(`guide.md` §7):

| 施策 | 判定 | 根拠 |
|---|---|---|
| **llms.txt** | Google 検索目的なら効果ゼロ | §7-1。Ahrefs 137,000 サイト調査で既存 llms.txt の 97% はトラフィックゼロ |
| **機械的なチャンキング** | 不要 | §7-2。「H2 に質問、下に 40〜60 語」の定型リライトは追加評価を生まない |
| **AI 向けの文体書き換え** | 不要 | §7-3。現代の AI は同義語と意味を扱える |
| **AI 専用スキーマ** | 存在しない | §7-4 |
| **FAQ の機械的な増設** | AI 引用目的なら効果なし | §7-2。人間と強調スニペット向けには依然有効なので、その目的でだけ足す |
| **見た目のリニューアル / 装飾強化** | SEO・AEO 目的ならやらない | §4-7。AI クローラーは CSS を見る前に捨てている。SEO でも影響度は内容の 0.5〜3。**内容の弱さをデザインで補うことはできない**。CVR / ブランド目的なら別途判断 |
| **図解を画像 (`<img>` / canvas) 化する** | やらない | §4-7。inline SVG のテキストは AI に読まれるが、画像化すると読まれなくなる。可視性の後退 |

### llms.txt の現状 (このサイト固有)

`src/app/llms.txt/route.ts` に実装済み。`sections` / `topics` / lessons から**動的生成**しており、
ページ追加に自動追随する。

- **削除の必要はない** — 保守コストがほぼゼロの形になっているため、§7-1 が警告する
  「保守コストが現実的な負担になるケース」に当たらない
- **ただし効果を期待しない** — Google 検索の可視性には効かない。ここを厚くする作業に
  時間を使わない。優先度は常に最下位
- 例外的に価値が出るのは Claude / OpenAI のエージェントが有意なリファラーになった場合 (§7-1)。
  そうなったら `taitech-analytics` で検知できる

### 逆に、判定が「やる」に倒れるもの

- 数値と出典を本文に足す (§3-4)
- 一次情報 (誤答分布 / 実測ログ / 出題傾向) を作る (§3-2)
- YouTube への展開 (§5-2)
- セマンティック HTML の改善 (§4-2)
- **表示速度 (LCP / INP) の改善** (§4-7) — 検索・AI・人間の 3 者すべてに効く数少ない施策。
  ただし競合が拮抗しているクエリでのタイブレーカーであり、内容の代わりにはならない

## 計測 (`guide.md` §9)

**順位だけを見ない。** Moz の 4 万クエリ調査では AI Mode 引用の 88% がオーガニック上位 10 位に
登場しない一方、Ahrefs は AI Overviews 引用の 38% が上位 10 位由来としている。
調査によって割れているが、**順位トラッキングだけでは判断を誤る**点は共通している (§2-2)。

- **従来検索チャネル**: `taitech-analytics` (GA4 / GSC)。既存の基盤で足りる
- **AI 引用チャネル**: **現状これを測る仕組みが無い**。追うなら最小構成は
  「代表プロンプトを月次で叩き、Presence (登場するか) と Citations (どの URL か) を記録」。
  提案する場合は `analytics/` 配下に置き、`taitech-analytics` のスキーマに合わせる
