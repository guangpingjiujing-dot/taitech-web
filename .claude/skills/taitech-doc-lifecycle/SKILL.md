# taitech-doc-lifecycle

**`docs/` の運用規約はこのファイルが SSoT。** `AGENTS.md` と `docs/README.md` にはポインタと
最小限の要約しか置かない。

モードは 3 つ: **kickoff**（着手時）/ **harvest**（圧縮時）/ **review**（月次の棚卸し）。

---

## ★ 置き場の決定表（何かを書く前に必ずここ）

判定は 2 問だけ。**「この記述は 1 年後も正しいか」「誰がいつ書き換えるのか」。**

| 事実の種類 | 寿命 | 置き場 | 書き換え方 |
|---|---|---|---|
| **コードから読める**（ページ一覧・型・props・定義文・キーワード） | — | **どこにも置かない** | `src/content/` と実装が一次情報 |
| **今の状態**（KPI・**実測値**・ブロッカー・次の 3 手） | 週〜月 | `docs/strategy/status.md` | **上書き**。100 行以内 |
| **未完了の意思**（やると決めたがまだやっていない） | 完了まで | `docs/strategy/roadmap.md` | **完了したら行ごと削除** |
| **起きたこと**（デプロイ・施策・実測・そのとき学んだこと） | 不変 | `docs/log/YYYY-MM-DD-<slug>.md` | **追記専用。書き換えない** |
| **判断の背景**（なぜその形か・何を捨てたか・覆す条件） | 永続 | `docs/sections/<name>.md` | harvest で更新 |
| **手順・運用ルール**（次に同じ作業をする人が従うもの） | 永続 | `.claude/skills/<name>/` | skill を更新 |
| **プロジェクト全体の慣習**（Tailwind の罠・テストの罠・ガードレール） | 永続 | `AGENTS.md` | 直接昇格 |
| **外部の状態**（アカウント・DNS・GA4・規約） | 不定 | `docs/site/operations.md` | 上書き |
| **開発中の作業**（設計書・進捗ログ・レビュー） | 数週間 | `docs/wip/<YYYYMMDD>-<slug>/` | 自由。冗長でよい |

**同じ事実を 2 箇所に書かない。** 片方をポインタにする。

### ⭐ 数値は `status.md` にしか置かない

**URL 数・PV・インプレッション・被リンク本数・記事本数・順位。これらを戦略ドキュメント
（`growth.md` / `seo.md` / `ideas.md` / `sections/*.md`）に書かない。**
書いた瞬間に更新責任者が消え、**診断より先に数値が腐る**。

2026-08-28 に 3 ファイルとも同じ形で腐っていた:

| ファイル | 腐っていた記述 | 実際 |
|---|---|---|
| `growth.md` §1 | 「URL 数 72 / X 投稿 12 件 / `/fe` 公開 2 日前」 | 144 / 15 件 / 25 日前 |
| `seo.md` ヘッダ | 「対象: 全 27 URL → 35 URL → 72 URL」 | 144 URL |
| `ideas.md` | 「現状 月 PV 500〜3,000 想定」 | 想定のまま一度も更新されず |

**数値の代わりに書くもの**は 2 つ。

1. **その判断が成立している条件**（例:「検索流入が立ち上がっていない」）
2. **条件が崩れたと判断する線**（例:「28 日で 500 impressions を超えたら SEO を主レバーに戻す」）

こう書けば、**数値が変わっても文章は正しいまま**で、かつ**いつ結論を捨てるかが自明**になる。
前例は `growth.md` §1「この診断が成立している条件」。

### ⭐ 相対表記を書かない

「2 日前」「約 4 ヶ月後」「来月」「直近」は書いた日を離れると意味が変わる。**必ず絶対日付**。
（`ideas.md` のセール表が「現在（2026-07-15）との関係」列を持っていて、1 ヶ月で全行が嘘になった）

### ⭐ 永続ドキュメントは「次回見直し」を持つ

`growth.md` / `seo.md` / `ideas.md` のように**長生きするのに追記トリガーが無い**ファイルは、
**ヘッダに `次回見直し: YYYY-MM-DD` を書き、同じ日付で roadmap にタスクを積む**。両方要る
（日付だけだと読まれない、タスクだけだとファイル側から辿れない）。

**日付は「その日に何が分かるか」で決める。** 適当な 1 ヶ月後ではない。
前例: `growth.md` / `seo.md` は 2026-09-26（4 本の効果測定が出揃う日）、
`ideas.md` は 2026-10-31（唯一の期限付き判断であるブラックフライデー記事のドラフト期限）。

### 各ファイルの制約

**`status.md`** — 100 行以内。溢れたら、それは log か roadmap か sections のどれか。
冒頭に「最終レビュー」の日付を持ち、月次の `/taitech-analytics review` の最後で更新する。

**`roadmap.md`** — 未完了タスクだけ。4 つの規約:
1. **完了したら行を削除する**（打ち消し線で残さない）
2. **削除する前に、その行に埋まっている恒久知識を移す** — 運用ルールなら skill、
   何が起きたかなら log。**タスク表は知識の置き場ではない**
3. **「期日 / 契機」を必ず埋める。** 日付が決まらないものはトリガーを書く
4. **番号を再利用しない**（log や `analytics/reports/` から参照されている）

**`log/`** — 1 デプロイ / 1 施策 = 1 ファイル。**書いたら二度と書き換えない。**
判定が覆ったら新しいファイルを書き、`supersedes:` / `superseded_by:` で結ぶ。
frontmatter（`date` / `slug` / `baseline` / `measure_on` / `status`）は
**全文を読まずに絞り込むため**のものなので必ず埋める。書式は `docs/log/README.md`。

**`wip/`** — **作業ストリーム単位**であってセクション単位ではない。同じセクションを後で大きく拡張するなら
新しい `wip/` を開く（`wip/20260910-fe-quiz-30/`）。名前に日付を入れるのは
「このフォルダはいつ死ぬのか」を自明にするため。

### 判断を書くときは「覆す条件」を併記する

**これを守らないと、撤回された判断が消えずに残る。** 実例: `roadmap.md` の「やらない判断」に
**「RDB インデックス以外の新規トピックを増やさない」が 1 年残り**、その間に実行した施策
（joho1 / fe-sql / query-plan / isolation-levels）のほぼ全部と矛盾していた。撤回する契機が
どこにも定義されていなかったのが原因。

前例として正しい形になっているのは `roadmap.md` #47 / #62（リダイレクト削除・301 判定）で、
**トリガーと最終期限の両方**を持ち、**トリガー未達でも期限で無条件に決着する**と書いてある。

# モード 1: kickoff（新セクション着手時）

1. `docs/wip/<YYYYMMDD>-<slug>/` を作る。**中の構成は自由**。
   設計書を 00-overview / 01-basic-design / 02-detailed-design に割っても、1 枚で書いてもよい。
   ここは `/compact` 対策が本業なので冗長でかまわない
2. `docs/sections/<name>.md` は**この時点では作らない**。harvest で初めて作る
3. `docs/strategy/roadmap.md` の「優先アクション」表に、実装タスクとは別に harvest タスクを積む:

   ```
   | NN | **wip/<slug> の harvest** (`/taitech-doc-lifecycle harvest wip/<slug>`)。
        デプロイ後の効果測定が終わったら実行 | docs の腐敗防止 |
   ```

   **この行を積むのがこのモードの最重要ステップ。** 圧縮の契機は時間ではなく
   「roadmap の表に載っているかどうか」でしか担保されない。ここを飛ばすと永久に来ない

4. 実装中に AGENTS.md 相当の知見（Tailwind の罠・テストの罠・共通化方針など)が出たら、
   wip/ に閉じ込めず **AGENTS.md に直接昇格**させる。セクション固有ではないものは
   `sections/` にも書かない

5. **デプロイした日に `docs/log/YYYY-MM-DD-<slug>.md` を書く。** wip/ の進捗ログではなく、
   log 側に「何を出したか / 捨てた案 / 実測 / 教訓」を残す。`measure_on` を埋め、
   **同じ日付の効果測定タスクを roadmap にも積む**（log と roadmap が対になる）

   > **日付は push した日。** 実装完了日ではない。効果測定の基準日がずれると
   > SEO 施策の評価期間がまるごと無駄になる（2026-08-07 に実際に起きた。
   > `docs/log/2026-08-07-title-shortening.md`）

# モード 2: harvest（圧縮時）

## いつ実行するか

**デプロイ直後ではない。** デプロイ後の効果測定が終わり、結果が `strategy/roadmap.md` に
書かれた時点（通常デプロイの 2〜4 週間後、`/taitech-analytics review` のタイミング）。

理由: デプロイ直後はまだ URL Inspection の残り・実機確認・GA4 の疎通確認が生きていて、
wip/ の進捗ログに仕事がある。効果測定が終わった瞬間、そのセクションは
「プロジェクト」から「存在するもの」に変わる。そこが境界。

**前倒しの合図**: wip/ のファイルに「このファイルは stale」「〜を一次情報とする」と
書きたくなったら、それは harvest すべきタイミングを過ぎているという意味。
警告を貼るのではなく harvest して消すこと。

## 判定基準

迷ったら一問だけ: **「これは `src/` を読めば分かるか？」** Yes なら捨てる。

### 残す（`sections/<name>.md` へ）

- **採用しなかった案とその理由、そして判断を覆す条件**
  （例:「imp 1,000 を超えたら top-level 化を再検討」）
- **明示的な非スコープ**（「模擬試験モードはやらない」「過去問は転載しない」）
- **実装が設計から逸脱した箇所とその理由**（「呼び出しスタックペインは情報量ゼロだったので削除」）
- **レビューで見送った指摘と、その反論**（採用した指摘は不要。コードに入っている）
- **コードのコメントに収まらない罠**（「`searchParams` を足すと Static が壊れる」）
- **未着手のまま残った拡張候補**、外部要因で止まっている残タスク（ASIN 未確定、GSC の手作業）
- **規約・法務の判断とその成立条件**（オマージュの商標リスクが低いと判断した 3 条件）

### 捨てる

- ファイル差分マップ / 追加ファイル一覧
- コンポーネントの props 表・API 定義・型定義
- 各ページの本文・定義文・FAQ・キーワード（`src/content/` が一次情報）
- 完了した TODO のログ、済んだデプロイ後チェックリスト
- 対応済みのレビュー指摘
- Phase 計画・工数見積・公開スケジュール（結果は roadmap にある）

## 手順

### 1. 退避（必須）

`docs/` は `.gitignore` 済みで **git 履歴が 1 件もない**。削除は復元不可。

```bash
tar czf <scratchpad>/docs-backup-$(date +%Y%m%d).tar.gz docs
```

### 2. 読む

`wip/<slug>/` を全部読む。加えて、乖離を検出するために実装側も見る:

```bash
ls src/app/<section>/          # 実際に存在するページ
grep -n 'slug: "' src/content/topics.<section>.ts
```

**設計書に書いてあるページ構成が現物と違うのは常態**。現物が正しい。

### 3. `docs/sections/<name>.md` を書く

テンプレート:

```markdown
# <セクション名> (`/<path>/*`)

**状態:** 本番公開済み (YYYY-MM-DD デプロイ)。<ページ構成>
**一次情報:** <実装ファイル>。本ファイルは決定の背景だけを持つ

## 1. 何を作ったか
<URL 表 + 想定読者 + 他セクションとの役割分担。10 行程度>

## 2. 意図的にやらないこと (非スコープ)
<「やってほしい」と言われたときに立ち返る決定>

## 3. コードから読めない決定と、その理由
### 3-1. <決定> — <理由>。覆すなら <条件>

## 4. 残タスク
<外部要因で止まっているもの、判断待ちのもの>
```

書き方の制約:

- **完了ログにしない。** 「完了」の羅列は wip/ の仕事。永続側は現在形で書く
- **絵文字・チェックマークを使わない**（プロジェクト方針）
- **15KB を超えたら書きすぎ。** 捨てる側の判定が甘い可能性を疑う
- セクションが大きすぎるときは分割してよい（前例: `data-modeling.md` と `er-diagram.md`）

### 4. 削除

```bash
rm -rf docs/wip/<slug>
```

### 5. 参照の追随修正

wip/ を指していた参照を潰す。**docs の外も見ること**:

```bash
grep -rn 'docs/wip/<slug>' docs/ AGENTS.md .claude/skills/ scripts/ src/
```

### 6. リンク切れチェック

```bash
python3 - <<'EOF'
import re, pathlib
bad = []
for p in pathlib.Path("docs").rglob("*.md"):
    for m in re.finditer(r'`(docs/[^`\s]+\.md)`|\]\((\./[^)]+\.md)\)', p.read_text()):
        t = m.group(1) or m.group(2)
        target = pathlib.Path(t) if t.startswith("docs/") else (p.parent / t)
        if not target.exists(): bad.append(f"{p}: {t}")
print("\n".join(sorted(set(bad))) or "リンク切れなし")
EOF
```

`{slug}` などのテンプレート表記が引っかかるのは正常。

### 7. 後始末

- `strategy/roadmap.md` の harvest タスクの**行を削除する**（打ち消し線にしない）
- `docs/README.md` のセクション一覧に新しい行が要るなら足す
- 圧縮率を報告する（例: 156KB → 8.4KB）

# モード 3: review（月次の棚卸し）

**追記の契機はあるが、見直しの契機が無かった** — これが 2026-08 に発覚した腐りの根本原因。
`/taitech-analytics review` の最後に、必ずこれを回す。

### 1. 腐りを機械的に洗う

```bash
# status.md が肥大していないか（100 行以内）
wc -l docs/strategy/status.md

# roadmap に完了行が残っていないか（0 であるべき）
grep -c '~~' docs/strategy/roadmap.md

# 期日 / 契機が空のタスクが無いか
grep -n '^| [0-9]* |  *|' docs/strategy/roadmap.md

# 測定日を過ぎたまま measuring のもの
grep -l "status: measuring" docs/log/2*.md | xargs grep -H "measure_on"

# 滞留している wip（roadmap に harvest タスクがあるか突き合わせる）
ls -d docs/wip/*/ && grep -c 'harvest' docs/strategy/roadmap.md

# 見直し日を過ぎた戦略ドキュメント
grep -Hn '次回見直し' docs/strategy/*.md

# 戦略ドキュメントに数値が紛れ込んでいないか（status.md 以外）
grep -nE '[0-9]+ *(URL|PV|imp|impressions|セッション|本|件|ページ)' \
  docs/strategy/growth.md docs/strategy/seo.md docs/strategy/ideas.md | head -20
```

最後の 1 本はノイズも拾う。**日付付きの実測記録なら残してよい**が、
「現状 N 件」の形は `status.md` へ移すか、条件と閾値の形に書き換える。

### 2. `status.md` を読み直して上書きする

**追記しない。上書きする。** 冒頭の「最終レビュー」を今日の日付にする。
KPI の現状 / 実測 / ブロッカー / 次の 3 手が、今日の認識と一致しているかだけを見る。

### 3. 撤回された判断が残っていないか

`status.md` と `sections/*.md` の中の「やらない」「〜しない」を拾い、
**この 1 ヶ月に実際やったことと矛盾していないか**を突き合わせる。矛盾していたら
**注記ではなく削除**する。覆す条件が書かれていない判断を見つけたら、その場で書き足す。

### 4. 見直し日が来た戦略ドキュメントを処理する

`次回見直し` の日付が過ぎているものを開き、**次の見直し日を必ず入れ直してから閉じる**。
日付を空にして閉じない。roadmap 側のタスクも同時に更新する。

### 5. 3 ヶ月以上動いていないタスク

roadmap に 3 ヶ月残っているタスクは、**やらないと決めるか、期日を入れ直すか**の
どちらかにする。「いつかやる」のまま残さない。

**「優先」と書かれたまま着手されていないものは特に疑う。** 優先度が高いのに動かないのは、
たいてい優先度の問題ではなく**着手の粒度が大きすぎる**（前例: `growth.md` の F は
2026-08-06 に「被リンクの本命」へ昇格したのに、3 週間 F-1 すら未着手だった）。

## 失敗パターン（実際に踏んだもの）

- **stale 警告で済ませる** — 2026-07/08 に er-diagram と fe-playground の設計書へ
  「00-02 は初期設計時のスナップショット」と自分で注記した。腐っていることは分かっていたのに
  消す契機がなく、エージェントは警告を読んだ上で古い内容を読み続けた。**annotate は解決ではない**
- **永続側に完了ログを溜める** — `03-implementation-status.md` は有用だったが、
  完了済み TODO の履歴が積もって 39KB になった。次に読む人が現状を掴むのに時間がかかる
- **同じ内容を docs と AGENTS.md の両方に書く** — Tailwind の罠・`getByRole("alert")` の罠は
  AGENTS.md に昇格済みなので、`sections/` 側には書かない（参照だけ）
- **圧縮タスクを roadmap に積み忘れる** — これが根本原因。積んでいないものは実行されない
- **1 つのファイルに性質の違うものを同居させる** — 旧 `roadmap.md` は現状 / 完了インベントリ /
  デプロイログ / 運用ルール / タスク / 期待値の **6 種類**を抱えて **803 行・52,000 トークン**になり、
  **Read の 1 回上限（25,000）を超えて読めなくなった**。しかも `docs/README.md` が
  「まずここ」と指していたので、全セッションがそのコストを払っていた
- **完了行を打ち消し線で残す** — タスク表 87 行のうち **48 行（バイト数で 61%）が `~~完了~~`** だった。
  読まれないのに毎回コンテキストを食い、そこに埋めた教訓（3 日ルール・カニバリの判定・
  BWT の翻訳バグ）は**誰にも見つからない**
- **運用ルールを寿命の短いファイルに書く** — インデックス登録の運用ルールが
  `strategy/index-requests.md`（「空になったら削除する」ファイル）に書かれていた。
  **キューを消すとルールも消える**構造になっていた
- **同じ規約を 3 箇所に書く** — docs のライフサイクル規約が AGENTS.md / `docs/README.md` /
  この skill に分散し、それぞれ少しずつ違っていた。**今はこの skill が SSoT**

## 実績

- **2026-08-07**: 4 セクション分を一括 harvest。**502KB → 38KB**（docs 全体は 700KB → 288KB）
- **2026-08-28**: `strategy/` の再設計。`roadmap.md` **126KB → 約 14KB**、
  デプロイ記録 23 本を `docs/log/` へ分離、`status.md` を新設、
  運用ルールを `/taitech-url-migration` とこの skill へ移送
