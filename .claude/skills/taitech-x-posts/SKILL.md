# taitech-x-posts

@taitech_dev の X 投稿履歴を markdown 化するスキル。

## スコープ

- **対象**: 投稿本文・投稿日・ハッシュタグ・本文中 URL・ピン留めの有無・（分かれば）投稿個別 URL
- **対象外**: impressions / likes / reposts などのエンゲージメント指標（プレーンテキストコピーには含まれない。将来 `analytics.x.com` CSV 対応時に別スキーマで追加予定）

## 前提

- **入力**: X プロフィールページ (`https://x.com/taitech_dev`) を開いた状態で `Ctrl+A` → コピー → 会話に貼り付けたテキスト
- **出力先**: `docs/x-posts/posted/YYYY-MM-DD-{slug}.md` （1 投稿 = 1 ファイル、flat）
- **既存ドラフト**: `docs/x-posts/YYYYMMDD-{slug}/post.md` は「投稿前のドラフト」の場所。今回作る `posted/` は「投稿後の履歴」の場所。両者は独立して共存する

## 手順

### 1. 貼り付けテキストから投稿ブロックを切り出す

- **開始マーカー**: 行として `{表示名}さんのポスト` が出現した次の行（例: `たいてっくさんのポスト`）
- **終了マーカー**: `おすすめ` `トレンド` `速報` などプロフィール外のサジェスト領域が出現した行の直前

各投稿ブロックの構造:

```
[固定]                   ← optional
{表示名}                 ← 例: たいてっく
@{ハンドル}              ← 例: @taitech_dev
·
{日付}                   ← 例: 7月17日   (年なし)
{本文複数行}
{リンクプレビュー領域}   ← optional
```

**リンクプレビュー領域** は 2 パターン。どちらも本文に含めない:
- 展開型: `{ドメイン}\n{カードタイトル}\n{カード説明}` （3 行、末尾が `…` で切れることあり）
- 折り畳み型: `{ドメイン}から` （1 行、例: `qiita.comから`）

見分け方: 次の `たいてっく`（handle） or 終了マーカーが来るまでを 1 ブロックとし、末尾側から「link preview っぽい行」を剥がす。判断が微妙な行は本文に残す（消し過ぎより残す方が安全）。

**重要**: カード領域は「本文に URL がなくてもリンクが存在する」ことを示すシグナルなので、剥がしたら必ず `link_card` フィールドに残す（下記 2 節参照）。カードだけあって本文 URL がないパターン (Qiita 自動投稿など) は珍しくない。「本文に URL がない = リンクなし」と判断しないこと。

**注意 (カード footer が欠落するケース)**: X の UI 状態・コピー方法によっては、本文中に URL があっても `{domain}から` の footer 行が Ctrl+A に含まれないことがある。この場合 `link_card` は無理に補わず省略する（後で別バッチで拾えた時に追記できるよう空けておく）。

### 1a. 前処理

#### おすすめアカウントブロックを除去

投稿一覧の前後や途中に、`@taitech_dev` 以外のアカウントの「おすすめ」ブロックが混ざることがある:

```
{アカウント表示名}
@{他のハンドル}
{アカウントの説明文}
```

`@taitech_dev` 以外のハンドルが現れるブロックは投稿ではないので skip する。実例: `@ClaudeCode_UT`, `@tenkijp_jishin`, `@MPD_bousai`, `@YahooTopicsEdit` など。

#### URL の改行分割を再構成

Ctrl+A では URL が **複数行に分割** されて出ることがある。例:

```
http://
taitech.dev/rdb-index/cove
ring
```

これは `http://taitech.dev/rdb-index/covering` の 1 本の URL。再構成ルール:

- 行末が `http://` または `https://` で終わる → 次の行以降と **空白なし** で結合
- 「URL 断片っぽい行」の判定: 空白を含まず、`.` `/` `?` `=` `&` `#` 等の URL 記号を含み、日本語文字を含まない
- 空行・ハッシュタグ・日本語本文が現れたら結合終了
- 再構成した URL を本文にも `links:` にも **1 行の URL** として書き出す

#### `￼` (U+FFFC) 文字はそのまま保存

絵文字や画像インライン要素が Ctrl+A で正しく取れず `￼` (OBJECT REPLACEMENT CHARACTER) に化けることがある。ブラウザや OS バージョンに依存する。取れないものはそのまま保存する（元の絵文字を推測して勝手に置換しない）。

### 2. 各投稿から情報抽出

| フィールド | 抽出ルール |
|---|---|
| `posted_at` | `{月}月{日}日` を `YYYY-MM-DD` に。年は「今日の日付」から逆算し **未来日にならない側** に寄せる。例: 今日 2026-08-01 で `7月17日` → `2026-07-17`。今日 2026-01-05 で `12月20日` → `2025-12-20` |
| `handle` | `@` の次の行から抽出（例: `taitech_dev`） |
| `is_pinned` | 直前に `固定` 行があれば `true`、無ければ `false` |
| `body` | 本文をそのまま保持（改行 / 絵文字 / 記号を改変しない。過去投稿の**忠実な**履歴記録なので現行スタイルガイド [[feedback_no_emoji]] に合わせて書き換えたりしない） |
| `tags` | 本文中の `#タグ` を抽出。配列で `#` を除いた文字列 |
| `links` | 本文中の `http://` / `https://` URL を配列で抽出（**カード内のリンクはここに入れない**。カードは `link_card` で別管理） |
| `link_card` | サムネイル / OG カードが付いていれば `{domain, title?, description?}` の dict。折り畳み型 (`{domain}から`) は `domain` のみ、展開型は 3 つとも埋める。無ければ省略 |
| `url` | 投稿個別 URL。Ctrl+A では取得できないので **空欄**。分かる場合のみ埋める（例: 対応ドラフトの `post.md` に `url:` があればそれを参照） |
| `source_draft` | 対応する `docs/x-posts/YYYYMMDD-{slug}/` があれば相対パス。無ければ省略 |

### 3. スラッグ生成

`YYYY-MM-DD-{slug}.md` の `{slug}` は以下ルール:

1. **既存ドラフトに対応するなら同じ slug を使う**。例: 本文が `docs/x-posts/20260721-weird-er-diagram/post.md` と同趣旨なら slug は `weird-er-diagram`
2. 対応なし & 独立投稿なら本文の主題を英語 kebab-case 2〜4 語で（例: `covering-index-article`, `normalization-site-launch`）
3. **同一日 & 同 slug が既にある** → 末尾に `-2`, `-3` を付ける
4. 明らかに Qiita 等の外部自動投稿と分かる場合は末尾に `-qiita` `-autopost` などを付けて区別

### 4. ファイル出力

`docs/x-posts/posted/YYYY-MM-DD-{slug}.md`:

```markdown
---
posted_at: 2026-07-17
handle: taitech_dev
url:
is_pinned: true
tags:
  - データベース
  - SQL
  - RDB
links:
  - http://taitech.dev/data-modeling/normalization/why
link_card:
  domain: taitech.dev
  title: なぜ正規化が必要か｜更新時異常 (挿入・更新・削除) を図解
  description: 正規化されていないテーブルで発生する挿入異常・更新異常・削除異常の 3 種類を図解で解説。同じ事実を複数行に持つことで起きる矛盾と情報損失、なぜ「一事実一箇所」が原則なのか。
source_draft: docs/x-posts/20260715-data-modeling
---

データベースの「正規化」を1から理解できるサイトを作りました。
✅正規化をする理由 / 関数従属性の基本
✅候補キー・スーパーキー・主キーの整理
✅第1〜第3正規化
実務でよくあるデータを題材に、図解を用いて分かりやすく解説しています。
http://taitech.dev/data-modeling/normalization/why
#データベース #SQL #RDB
```

### 5. 冪等性

- 出力先に**同名ファイル**が既に存在:
  - 本文が実質同じ → skip（ユーザーに「N件 skip」と報告）
  - 本文が異なる → 差分を提示して確認（上書き / 別 slug で保存 / skip）
- ユーザーが同じ日を複数バッチで貼っても壊れないようにする
- **部分バッチ対応**: プロフィール末尾までスクロールしていないコピーでも、拾えた分だけ処理。「プロフィール冒頭に `{N} 件のポスト` とあるが今回パースできたのは {M} 件」と報告

### 6. ドラフト側ステータスの同期

各 posted ファイルに `source_draft:` が設定されている場合、そのドラフト (`docs/x-posts/{YYYYMMDD-slug}/post.md`) の frontmatter を以下ルールで更新する:

- `status: draft` → `status: posted` に変更
- `posted_at: {投稿日 YYYY-MM-DD}` を追加（無ければ）
- `posted_ref: docs/x-posts/posted/YYYY-MM-DD-{slug}.md` を追加（無ければ）
- `url:` は既存値を尊重（`（投稿後に追記）` プレースホルダのままで OK。X 個別 URL は Ctrl+A では取れないため）
- 既に `status: posted` でも `posted_at` `posted_ref` が欠けていれば追加（過去分の遡及補完）
- ドラフト本文 (`## フック（ひとこと）` 以下) は改変しない — 設計メモとして残す

**注意**: ドラフトと実投稿本文は細部が違うことが多い（例: hashtag の追加削除、絵文字の有無）。**ドラフトを実投稿に合わせて書き換えない**。実際の投稿本文は `posted/*.md` 側が SSoT で、ドラフト側は「投稿前の設計スナップショット」として historical value がある。

### 7. README 更新

`docs/x-posts/README.md` を以下 2 箇所とも更新:

1. **ドラフト一覧テーブル** (先頭近く): 上記ステップ 6 で状態変化したドラフトの行を反映
   - 列: `ドラフト日 / スラッグ / トピック / ステータス / 投稿日 / X URL`
   - ステータスは `下書き` or `投稿済み`
   - `投稿日` `X URL` は既知の値を埋める（不明は `—`）
2. **投稿済みアーカイブ (`posted/`) セクション** (末尾): 投稿日順の最新一覧に更新

## 実行後の報告

以下を短く報告して終わる:

- 新規に作った投稿 markdown の数と一覧
- skip した件数（既存と同一）
- 上書きした件数（あれば）
- **ドラフト側で status を更新した件数**（および同時に `posted_at` / `posted_ref` を補完した件数）
- プロフィールヘッダの `{N} 件のポスト` と実パース件数の差分（部分バッチ検出）
- `url:` が空欄で残った件数（後で手動補完が必要）

## 制限事項

- **投稿個別 URL は取れない**: Ctrl+A テキストからは拾えない。空欄で書き出す。手動で埋める場合は X で該当投稿の日時をクリックして URL をコピーする
- **リポスト / 引用ポスト / 返信の判別困難**: 現状「ポスト」タブのみを対象。返信タブ / メディアタブは別途対応
- **年またぎの誤判定**: 「未来にならない側に寄せる」ヒューリスティックが誤る場合は手動修正
- **エンゲージメント数値なし**: 前述の通り将来別スキーマで対応

- ユーザーが X プロフィールのテキストを貼って「markdown 化」「アーカイブ」「x-posts 更新」等を依頼
- ユーザーが `/taitech-x-posts` 相当の意図で呼び出したとき
