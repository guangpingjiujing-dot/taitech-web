# x-algorithm-posting

X が公開した For You アルゴリズムの実装を読んで、**何がスコアに効き、何が効かないか**を
投稿文の設計に翻訳するスキル。

## 大原則（これを外すと全部ずれる）

1. **アルゴリズムが最大化しているのは「閲覧者がその投稿に対して取る行動の予測確率」の加重和。**
   投稿の「良さ」を直接評価する関数は存在しない。文字数も改行も投稿時刻もスコア式に出てこない。
   効くのは「その文面を見た人が、いいねより上位の行動を取りそうか」だけ。

2. **重みは予測確率に掛かる。生の件数ではない。**
   「通報1件がいいね468件を打ち消す」式の換算は誤り（`param.rs:278-305` にコードコメントで
   明記されている）。負の重みが大きいのは、通報の基礎発生率がいいねの1/1000以下だから
   正規化しているだけ。

3. **スコアは閲覧者ごとに違う。**「バズる投稿」という単一のスコアは存在しない。
   Phoenix はポストのマルチモーダル埋め込み由来のセマンティックIDと、閲覧者の行動履歴を
   突き合わせる。**誰か特定の人に刺さる形に振り切る方が、万人向けに薄めるより強い。**

4. **数値は 2026-08-25 時点のデフォルト値で、A/B テストで上書きされうる。**
   断定の根拠にはせず、優先順位を決める地図として使う。ユーザーに説明するときも同じ温度で話す。

5. **`references/algorithm-facts.md` が根拠。** このファイルは翻訳であって条文ではない。
   数値や条件を確認するときは必ず reference を開く。行番号付きで引用元が書いてある。

## 使い方 — 3 モード

ユーザーの発話から判断する。

| モード | 起動する発話の例 | やること |
|---|---|---|
| **design** | 「この記事の告知ポスト書いて」「新しいポスト考えて」 | 書く前に §A を通す |
| **review** | 「このドラフトどう?」「なんで伸びなかった?」 | §B で診断する |
| **judge** | 「ハッシュタグ減らした方がいい?」「リンクは1st リプに置くべき?」 | §C の判定ゲートに通す |

## §A design — 投稿を設計する

### A-1. レバレッジの梯子（重み順）

**上から順に「その行動を取りたくなるか」を自問する。**

重みの読み方に注意。「重み20 は 重み0.5 の40倍」が意味するのは
**「予測確率が同じだけ上がったときのスコアへの寄与が40倍」**であって、
「コピー共有1件 = いいね40件」ではない（大原則2）。
実務上の含意は単純で、**上の段を1つ動かす方が、下の段を大量に積むより効率がいい**。

| 段 | 予測アクション | 重み | 設計上の問い |
|---|---|---:|---|
| **1** | リンクをコピーして共有 | **20.0** | これを**誰かに送りたく**なるか。送る相手の顔が浮かぶか |
| **1** | 返信（相互フォロー×オリジナル投稿） | **20.0** | 相互フォローの人が**一言返したく**なる余白があるか |
| **2** | 引用ポスト | 5.0 | 引用して**自分の一言を足せる**形か |
| **2** | DM で共有 | 5.0 | 1on1 で送る価値があるか |
| **2** | 著者をフォロー | 4.0 | この1投稿で「この人は何の人か」が分かるか |
| **3** | 共有 / リポスト | 2.0 / 1.0 | 自分のTLに置いて恥ずかしくないか |
| **4** | いいね | **0.5** | ← ここを狙うのは費用対効果が悪い |
| **4** | クリック / リンクを開く | 0.4 / 0.2 | 続きを読みたくなるか |
| **5** | 滞在（dwell） | 0.05 | 一瞬止まるか |
| **負** | 興味がない / ミュート / ブロック / 通報 | -43.2 / -58.8 / -31.2 / -234.0 | **苛立たせないか** |
| 負 | 滞在しなかった | -0.02 | （ほぼ無視してよい） |

### A-2. 段ごとの具体的な打ち手

**第1段 — 転送されるか（重み20）**

`ShareViaCopyLink` が単独で最大の重みを持つ。
コピーして送るのは、**受け取る相手が具体的にいるとき**だけ。

- 名指しされた読者を本文に置く: 「新人にインデックスを説明する立場の人へ」
- 保存価値のある単位で完結させる: 判断基準・チェックリスト・落とし穴の一覧
- 「あとで見返す」が成立する具体性（曖昧な一般論はコピーされない）

**第1段 — 相互フォローが返信するか（重み20）**

`ReplyWeight 5.0 + BidirectionalFollowReplyWeightBoost 15.0`。ただし
**オリジナル投稿にしか掛からない**（返信・リポストは対象外、`ranking_scorer.rs:180-184`）。

- 完全に閉じた投稿には返信できない。**断定 + 余白**の構造にする
  （「自分はこう判断している。例外があれば知りたい」）
- 経験の差が出る論点を選ぶ（「これ現場だとどうしてる?」に自然に繋がる）
- **注意**: 露骨なエンゲージメント誘導は逆効果。`grox/flows/reply_spam/` に
  協調スパム・返信スパムの LLM 検出器がある

**第2段 — 引用されるか（重み5）**

賛否が分かれる主張、または読者が自分の事例を接ぎ木できる型。
「◯◯は不要」のような煽りではなく、**根拠のある非自明な主張**。

**第2段 — フォローされるか（重み4）**

1投稿単体で「この人は何の専門か」が伝わるか。プロフィールクリックの重みは **0.0** なので、
「プロフィールを見てもらう」導線には価値がない。**投稿の中で完結させる。**

**負のシグナル — 非対称性を理解する**

無視される (-0.02) と苛立たせる (-43.2) では**桁が3つ違う**。
釣り見出し・過剰な断定・煽りは、リーチを広げる代わりに `NotInterested` の予測確率を上げる。
**期待値ではマイナスになりうる。** 「刺さらない人には静かにスルーされる」形が最適。

### A-3. 構造的な制約（文面より先に効く）

| 制約 | 数値 | 運用への翻訳 |
|---|---|---|
| **投稿の寿命** | 48時間（`AgeFilter`） | 48時間で候補プールから消える。それ以降の再浮上はない |
| **自分で自分を食う** | 2本目 ×0.625、3本目 ×0.4375、下限 ×0.25 | **主力投稿は48時間空ける。** 同じ48時間窓に複数出すと後続が減衰する |
| **返信・リポストは OON に届かない** | `OONRetweetReplyFilter` で全削除 | **リーチ目的の運用はオリジナル投稿一択。** 返信は「相互フォローを増やす」ための投資としてのみ意味がある（→ 将来の重み20の前提になる） |
| **フォロワー向けでも返信/リポストは ×0.75** | `EnableOonRescoreForInNetworkRepliesRetweets` | セルフスレッドの2本目以降も対象 |
| **非フォロワー配信は ×0.75** | `OonWeightFactor` | 新規リーチには約1.33倍のスコアが要る |
| **小規模著者ブースト** | フォロワー≤1000 かつ インプレ<1000 かつ **24時間以内** → 15〜16位相当に押し上げ | 該当するなら**投稿後24時間が勝負**。この窓で初速が付くかで決まる |

**セルフスレッドについて**: `SelfReplyChainFilter` では落ちない（祖先が全部自分なら通す）が、
返信である以上 `OONRetweetReplyFilter` で非フォロワーには届かない。
既存の `docs/x-posts/README.md` の「単発投稿を基本にする」方針は**コードで裏付けられる。**

### A-4. トピックの一貫性

Phoenix は著者IDの埋め込みを（retrieval では）持たない。ポストのセマンティックIDと
閲覧者の行動履歴のマッチで配信先が決まる。
→ **アカウントの信用ではなく、投稿単体の意味ベクトルが配信先を決める。**
トピックがブレると、過去の投稿で届いた層に次が届かない。

加えて Grox の VLM が全ポストを読んで `taxonomy_categories`（トピック分類 + スコア）を付ける。
**分類が曖昧な投稿は、トピック経路に乗り損ねる。** 何の話か1行目で確定させる。

## §B review — ドラフトを診断する

順に潰す。上ほど重い。

**B-1. 致命的な構造（該当したら文面を直しても無意味）**

- [ ] オリジナル投稿か（返信・リポストなら OON リーチはゼロ）
- [ ] 直近48時間に自分の他の投稿がないか（あるなら片方を後ろにずらす）
- [ ] 可視性フィルタに引っかかる要素はないか（外部リンク先の健全性、他者になりすまし
      と読める表現、NSFW 判定されうる語）→ 詳細は `references/algorithm-facts.md` §5

**B-2. レバレッジの梯子（A-1 の各段に対して）**

- [ ] **誰に送るか**を具体的に言えるか（言えないなら重み20を捨てている）
- [ ] 相互フォローが**一言返せる余白**があるか（完全に閉じていないか）
- [ ] 引用して**一言足せる**形か
- [ ] この1投稿で**何の人か**が分かるか
- [ ] いいねだけを取りに行っていないか（共感だけの投稿は 0.5 しか取れない）

**B-3. 負のシグナル**

- [ ] 特定の層を苛立たせる書き方をしていないか（`NotInterested` の重みは -43.2。
      「興味なし」を押されそうな確率がわずかに上がるだけで、正の寄与を丸ごと打ち消す）
- [ ] 見出しと中身が乖離していないか（釣りは `NotInterested` を直撃する）
- [ ] エンゲージメント誘導が露骨でないか（返信スパム検出器がある）

**B-4. taitech-web 側の既存規約**（`docs/x-posts/README.md` / `AGENTS.md`）

- [ ] weighted length ≤ 280 を**機械で数えた**（`python3 docs/x-posts/count.py <path>`）
- [ ] 絵文字を使っていない
- [ ] ハッシュタグ 4〜5 個まで
- [ ] URL は `taitech.dev/...` を直貼り（トラッキングパラメータなし）
- [ ] 構成は フック → 要点 → CTA URL → ハッシュタグ

**B-5. 「伸びなかった」の診断**

インプレッションが低い場合、原因の切り分けはこの順:

1. **OON にそもそも出ていない** → 返信/リポストだった、または可視性フィルタの
   OON drop ラベルが付いている。X の "Under the Hood" 透明性ツールでラベルを確認する
2. **48時間窓に自分の投稿が重なっていた** → 著者多様性の減衰
3. **初速が付かなかった** → 小規模著者ブーストの24時間窓を逃した
4. **文面の問題** → ここでようやく §B-2

**1〜3 を確認せずに文面のせいにしない。**

## §C judge — 「◯◯した方が伸びる」の判定

コードで確認できる話とできない話を切り分ける。

| 通説 | 判定 | 根拠 |
|---|---|---|
| **リンクを貼ると reach が落ちる** | **コードに根拠なし。** `OpenLinkWeight` は **+0.2**（正） | `param.rs:335`。ただし `MaliciousUrlOonDropRule` はある |
| **リンクは1st リプに置くべき** | **逆効果。** 返信は OON に一切届かない | `oon_retweet_reply_filter.rs:13-21` |
| **いいねを増やせば伸びる** | 弱い。いいねは 0.5 で最下位クラス | `param.rs:307` |
| **通報されるとリーチが死ぬ** | 誇張。予測確率への係数であり、パーソナライズされている | `param.rs:288-305` のコードコメント |
| **相互フォローを増やすと伸びる** | **正しい。** オリジナル投稿の返信重みが 5→20 になる | `ranking_scorer.rs:180-193` |
| **スレッドにすると伸びる** | 伸びない。2本目以降は返信扱いで OON ゼロ | 同上 + 既存の投稿方針 |
| **1日に複数回投稿すると伸びる** | 48時間窓では**逆効果**。2本目 ×0.625 | `ranking_scorer.rs:561-563` |
| **投稿時刻が重要** | **コードに根拠なし**（ローカル時刻は特徴量にあるが優遇するコードはない） | `phoenix/README.md:182-187` |
| **文字数・改行が重要** | **コードに根拠なし** | 該当コードなし |
| **ハッシュタグは少ない方がいい** | **コードでは確認できない。** スパム判定は LLM 側でプロンプト非公開 | `grox/flows/upa/prompts.py` |
| **新規アカウントは不利** | 逆。フォロワー≤1000 には24時間のブーストがある | `author_cold_start.rs` |
| **新しい投稿はモデルに認識されるまで時間がかかる** | 誤り。ハッシュ埋め込みで即座に表現可能 | README "Key Design Decisions" #3 |

**判定できないものは「コードでは確認できない」と正直に言う。**
推測を数値で装飾しない。ハッシュタグ本数のような既存の運用ルールは、
コードに根拠がなくても**経験則として維持してよい** — ただし「アルゴリズム的に正しい」とは言わない。

## 制限事項

- **この分析は For You タイムラインのみ。** 検索・通知・Following タブ・プロフィール流入は別系統
- **数値は 2026-08-25 時点のデフォルト。** A/B テストで上書きされうる。
  リポジトリを再クローンして差分を見れば更新できる（`git log` に日次のコミットがある）
- **Grox のプロンプトと一部の botmaker ルールは非公開。** 「何が高品質と判定されるか」
  「何がスパムと判定されるか」の基準はコードから読み取れない
- **`slop_score` / `isHighQuality` の消費側がリポジトリ内にない。** 生成されているのは
  確実だが、どうランキングに効くかは追えない
- **VMRanker が最後に並べ替える。** その中身（`vm-ranker/`）まではこのスキルで追っていない
